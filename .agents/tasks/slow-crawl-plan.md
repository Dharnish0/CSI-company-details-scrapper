## Design decisions (made here, with reasons)

- D1 Limiter lives in `agents/ratelimit.py` (pure, clock/sleeper injected, `threading.Lock`), owned by the single `LLMGateway`. Every agent call goes `AgentRunner -> LLMGateway.complete -> provider.complete` (verified: `app.build_runtime` builds one gateway; nothing else calls `provider.complete`), so a gateway-level slot is global across extraction, website_resolution, relationship_verification, discovery, dedup, validation and advisor. Cache hits and budget/circuit skips return in `AgentRunner._invoke` before the gateway, so they cannot consume the interval (a test proves it).
- D2 In slow mode the limiter replaces `RequestPacer` (`pacer=None`); `LLM_RPM_LIMIT/LLM_TPM_LIMIT` are ignored with a startup log line, because the quota findings show those were mis-set (200000/600 vs real 8000 TPM, 30 RPM) and double sleeping would add waits. Default mode keeps `RequestPacer` untouched.
- D3 The gap is measured start-to-start. After each response: `gap = max(interval * m, tpm_gap, reset_gap, retry_after_gap)`. `m` is the backoff multiplier (x2 per 429, cap 8; x0.85 after every 3 consecutive successes, floor 1.0). `tpm_gap = ewma_tokens_per_request / (0.70 * limit_tokens) * 60`, where `limit_tokens` is the observed `x-ratelimit-limit-tokens`, else `SLOW_CRAWL_TPM_LIMIT` (8000). `reset_gap = x-ratelimit-reset-tokens` when remaining tokens < max(1000, 15% of limit); `x-ratelimit-reset-requests` when remaining requests <= 5. The first request after start/resume is immediate.
- D4 Projected tokens for TPM use `estimated_input + min(max_output_tokens, ewma_completion or 1000)`, not `max_output_tokens`. Reason: the findings show `input + 3000` reaches about 8,700 > 8,000 TPM, which would block forever, and lowering `max_output_tokens` would change the response-cache key (45 cache hits would be lost). A single request larger than the window waits at most one 60 s window, then proceeds and lets the provider decide.
- D5 Groq reports requests in the per-day bucket (RPD 1000) and tokens in the per-minute bucket (TPM 8000). TPD 200,000 is not in headers. The limiter keeps a local TPD token-bucket estimate (capacity `SLOW_CRAWL_TPD_LIMIT`=200000, refill limit/86400 per second; 0 disables), seeded at start by replaying the last 24 h of `agent_invocations` tokens, and waits proactively only when the estimated level is below the request estimate. A sliding 24 h window is wrong here: the findings show a continuous refill (575 s Retry-After = 1,330-token deficit). A 429 is authoritative and overrides the estimate.
- D6 429 classification (`classify_429(detail, retry_after_s)`): text containing "per day", "(tpd)" or "(rpd)" => `day`; "per minute", "(tpm)" or "(rpm)" => `minute`; otherwise `day` if `Retry-After` > 65 s else `minute`. Minute: honor `Retry-After` plus a positive jitter of 0-5% (at most 2 s), retry in-call up to `LLM_RATE_LIMIT_RETRIES`. Day: no in-call retries; the cooldown equals the stated `Retry-After` (+ jitter), or `SLOW_CRAWL_DAILY_RETRY_SECONDS` (900) when absent.
- D7 No schema migration. Wake time = `research_queue.not_before` (day cooldown sets `not_before = max(existing, wake)` on all PENDING tasks). The 429 counter is derived from `agent_invocations.response_json -> transport.errors` ("RATE_LIMITED" entries, via `json_each`), so no counter column. The session state (pid, start, deadline, token/cost baselines, state, sleeping-until, heartbeat) lives in the instance lock/session JSON file next to the DB. This avoids touching `runs`, which the existing `migrate_db` rebuilds only for the `PARTIAL` CHECK.
- D8 Ceilings are per session (per process start), measured against a baseline read at start: `session_tokens = runs.llm_tokens_used - baseline`. Reason: the user's run already holds 210,224 tokens, so a total-based 250K ceiling would leave 40K; `runs.llm_token_budget` stays NULL and is not modified. A `SessionCeiling` is passed to `BudgetGuard`; denial reasons contain `TOKEN_BUDGET` (`TOKEN_BUDGET_SLOW_CRAWL_CEILING`, `TOKEN_BUDGET_SLOW_CRAWL_COST_CEILING`) so the existing `"TOKEN_BUDGET" in why` checks in `graphs/research.py` already stop with run scope; no edit to `research.py`. The stored status is `BUDGET_EXHAUSTED` (label `BUDGET_STOPPED`). Cost is derived from `LLM_PRICE_IN_PER_MTOK/OUT`; no Groq prices are hard-coded (unverifiable offline). If prices are 0 and a cost ceiling is set, startup warns that it is inert.
- D9 In slow mode only, `BudgetGuard.llm_calls()` for the run-level cap excludes 429-failed invocations with `transport.requests = 0` (as the per-task count already does since `4ed9d51`). Otherwise 24 h of waiting would burn `MAX_LLM_CALLS_PER_RUN` (the user's run is at 77 of 150 with 24 such rows). Default mode keeps the current count.
- D10 The supervisor loop is the existing `Supervisor.run` with `if self.slow is not None` hooks (idle wait, 429 reschedule, loop-top stop checks, interrupt handling), implemented by a `SlowCrawlController` in `graphs/slow_crawl.py`. Reason: one loop means the same claim, commit, finalize and `final_status()` logic in both modes. Stop outcomes: queue empty => existing COMPLETED/PARTIAL/FAILED; max runtime or interrupt => PAUSED (resumable); ceiling => BUDGET_EXHAUSTED. New exit codes: `EXIT_INTERRUPTED=5`, `EXIT_LOCKED=6` (all others unchanged).
- D11 Shutdown: first SIGINT/SIGTERM/SIGBREAK sets a flag. The in-flight HTTP request finishes (its tokens are recorded), `limiter.acquire` then refuses, and the supervisor requeues the running task with attempts unchanged (PENDING, `attempts-1`) regardless of the graph outcome, because the re-run is served from the response cache and commits are idempotent. A second signal raises `KeyboardInterrupt`, which the supervisor catches around `research.run` and handles the same way. Sleeps use `Sleeper.sleep` in chunks of `SLOW_CRAWL_SLEEP_CHUNK_SECONDS` (30, max 60).
- D12 Single-instance guard: `<db_path>.slowcrawl.lock` created with `O_CREAT|O_EXCL` holding JSON `{pid, started_at, run_id, ...}`. An existing lock whose pid is alive => refuse (exit 6, the message names the pid and the file). A dead pid, or a corrupt file older than 60 s => stale, reclaimed with a log line. A live pid is never overridden even if the heartbeat is old (a suspended laptop would otherwise get two crawlers); the message tells the user how to remove it by hand. Applies to `run`/`resume` only when slow mode is on.
- D13 Gaps/assumptions: (a) real Groq account limits equal the documented base table (8K TPM, 30 RPM, 1K RPD, 200K TPD); the limiter prefers observed headers. (b) `progress` reads the WAL DB through `connect_readonly`, which creates zero-byte `-wal/-shm` files beside it (seen in the findings); that is SQLite housekeeping, not a data change. (c) Estimated cost is shown from `runs.llm_cost_usd`; with unset prices it prints "prices unset".
